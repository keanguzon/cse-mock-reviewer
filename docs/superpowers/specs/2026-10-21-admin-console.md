# Admin console specification

Date: 2026-10-21. Status: proposed for approval; implementation has not started.

## Outcome and boundaries

Provide a small private admin console for approximately 2–10 reviewer users. The primary flow is Users → a user → exam history/performance → delete one or selected exams. The reviewer continues to use Google sign-in; the administrator uses a separate email/password account at `/admin/login`.

- Preserve existing reviewer routes, navigation, fonts, colors, component appearance, spacing, and button sizes.
- Reuse the existing dark purple theme, DM Sans body font, Syne brand, Bulma classes, Lucide icons, cards, inputs, and confirmation styling for admin screens. Add scoped admin CSS only.
- Do not add dependencies unless an implementation finding demonstrates a concrete need.
- Do not change question content, grading, exam configuration, or selection weights as part of this feature.
- No deployment, production database mutation, account provisioning, commit, or push is authorized by this planning request.
- Existing markdown files are ignored; preserve `.gitignore` and do not infer authorization from the older checkpoint.

The checkpoint and code agree that `attempts.ts`, `pendingAttempts.ts`, and `attemptSync.ts` are foundations only. `syncStore.svelte.ts` still inserts directly into `exam_attempts` and separately upserts progress. `ResultScreen.svelte` currently reports saved immediately. There are no server admin/auth helpers. Root `+layout.svelte` always renders the reviewer Google menu. This feature must integrate the minimum saving/recovery changes necessary for deletion correctness; it does not finish the entire previous reliability plan.

## Admin identity and sessions

Use Supabase Auth email/password for a dedicated administrator identity. Provision it through a controlled operator step after deployment approval, with a confirmed email and strong password. Insert its UUID into `private.admin_memberships`; there is no console signup, invite, role editor, password recovery, or account creation screen. Public signup or user-editable `user_metadata` never confers membership. The dedicated account must differ from existing reviewer account UUIDs; do not link its email/provider identities to the reviewer's Google account.

All `/admin/**` requests, including data endpoints, are checked server-side. The login page and login POST are the only unauthenticated exceptions. Every protected request validates an opaque session, calls Supabase `auth.getUser(accessToken)` using a request-isolated client, and checks current DB membership and lifecycle. Expired/revoked membership fails closed; an outage returns 503 without serving cached private data. API requests receive 401/403; pages redirect to `/admin/login` with a fixed safe return path.

Use server-managed opaque sessions instead of the reviewer browser client: a 32-byte random token in `cse_admin_session`, `HttpOnly`, `SameSite=Strict`, `Secure` in HTTPS, path `/admin`, no Domain. Store only its SHA-256 hash as the lookup key in `private.admin_sessions`. Store the Supabase access token encrypted with AES-GCM under server-only `ADMIN_SESSION_ENCRYPTION_KEY`; discard the refresh token. Sessions expire at the earlier of the Supabase access token expiry or 60 minutes after login; no silent refresh in v1. Reauthenticate to extend an expired session. Logout removes the opaque session and cookie without signing out the Google reviewer session. Admin credentials/tokens never enter localStorage, page data, client bundles, URL parameters, logs, or the reviewer Supabase singleton.

Server-only configuration: `SUPABASE_SERVICE_ROLE_KEY`, `ADMIN_SESSION_ENCRYPTION_KEY` (32-byte base64), `ADMIN_ALLOWED_ORIGIN`; use the existing public URL/anon key for password authentication. Fail closed if required server settings are missing. Keep a service client separate from the credential-checking client, both with persistence, URL detection, and auto-refresh disabled. SvelteKit server-only import boundaries must reject accidental client imports.

Keep SvelteKit origin protection enabled. Every state-changing admin POST requires exact configured Origin, supported content type, and a session-bound CSRF token. Login uses a short-lived preauth nonce cookie/form pair plus Origin; protected forms/JSON use a token whose hash is held in the session. Reject unsupported methods, missing Origin, and cross-site requests. GET is read-only. Use `Cache-Control: private, no-store`, `Vary: Cookie`, no CORS grants, frame-ancestors none, and Referrer-Policy same-origin on admin responses. A DB-backed login throttle allows at most five failures per normalized email or hashed client IP per 15 minutes; return a generic error/429 and do not log passwords. Do not trust arbitrary forwarded IP headers.

Hard deletion requires successful password reauthentication by the same session/admin identity within five minutes; store `reauthenticated_at` server-side and rotate the session/CSRF secret. Query current membership again for destructive DB operations, not only in a page load. Deny self-targets and any current admin target in every reset/delete endpoint and DB mutation; normal console cannot remove administrators.

## Screens and useful controls

`/admin/login`: email/password, generic failures, loading state, no Google button/signup. `/admin`: concise totals for reviewer accounts, completed exams, paused exams, and unresolved deletion operations; links to Users and Audit. Define totals from current stored records; do not infer online users or expose passwords/tokens.

`/admin/users`: name, email, created date, exam count, last completion, and account/deletion status. Search name/email, filter all/with exams/without exams/deletion pending, sort name/email/created/latest exam, stable UUID tie-breaker, pagination of 20/50 rows (20 default), Refresh, loading/error/empty states. Admin accounts may be shown as protected; destructive controls are disabled and server-denied. User selection navigates to `/admin/users/[id]`; no bulk account deletion.

`/admin/users/[id]`: identity, remaining-exam performance summary, history table, and separate Reset progress / Delete account controls. Exam rows show completion date, score/total/percentage, category, mode, and level, with an optional expandable snapshot review. Render question/name/email text safely; do not reuse unchecked HTML rendering. History search matches category or exact attempt UUID; filters are mode, level, category and inclusive UTC date range; sort completion/percentage/category with UUID tie-breaker; 20/50-row pagination and Refresh. Performance cards use all remaining exams, independently of the table filters, and say so.

Gmail-style selection applies only to this user's exams: per-row checkbox, page select-all with indeterminate state, count, Clear selection, and an explicit “Select all N matching exams” action after selecting the page. Never silently expand page selection. Preserve selected IDs across pagination; changing user/search/filter/sort or Refresh clears the selection. Unchecking rows after all-matching selection switches to explicit IDs from that snapshot. Zero selection disables Delete. A single-row delete uses the same preview/confirmation mechanism.

The explicit “Select all N matching exams” action immediately creates a sealed server selection. Explicit-ID selections are sealed when opening confirmation. Store random ID, actor session, target user, canonical query, fixed UUID list, generation, revision, count, creation time, five-minute expiry, and one-use status; return the authorized frozen IDs for checkbox state. Unchecking in matching mode derives/reseals a subset of that existing snapshot; validate the parent snapshot and exclude only its IDs, never rerun the original query or broaden selection. Revalidate the sealed selection when opening confirmation. Browser submits only selection ID and idempotency operation UUID when executing. Confirmation states target email, exact count, permanent deletion, and analytics/progress recalculation. Cancel is default; busy state prevents duplicate submissions. Changed revision, expiry, ownership or targets returns 409 requiring a fresh preview; never add newly created matching exams. Repeated operation UUID returns its saved outcome.

Reset progress has its own sealed confirmation bound to the target, actor session, generation, revision, exact exam count and five-minute expiry: delete all completed exams, paused exam, and algorithm progress while preserving the Auth account and profile. Execution consumes that preview once; a newer attempt/session or other revision change requires a new confirmation instead of silently erasing new data. Account hard-delete has two distinct confirmation steps: impact preview, then exact current target email plus fresh administrator password reauthentication. Recheck the email at execution. No mass account deletion, impersonation, public role editing, exports, email notifications, chart-builder, or account-management expansion.

`/admin/audit`: paginated recent actions with actor identity, target UUID, operation ID, action, counts, timestamp and succeeded/failed/partial/pending state; filter action/status/target. Include login failure/success, logout, selection deletion, reset, account deletion and retries. Do not store question/answer snapshots, credentials, raw IP addresses, or full user email in audit payloads. Retain actor/target UUIDs as historical values without cascading foreign keys. Failed requests write sanitized failure records when DB availability permits; never claim a durable audit on database failure.

Keyboard checkboxes and controls, visible focus, accessible names, aria-live selected count/status, focus-trapped confirmation dialogs, Escape/cancel and focus return are required. At 390px use wrapping toolbars and a contained horizontally scrollable table; prevent page overflow. Keep existing reviewer global styles intact.

## Analytics and algorithm rebuild

Historical attempt snapshots and stored scores remain authoritative; never regrade from today's question bank. Extract the current dashboard aggregation into a shared pure helper for admin/reviewer use without changing results: exam count, best rounded percentage, rounded arithmetic mean of per-exam percentages (not weighted), and per-category totals from stored questions/answers. For legacy rows with no usable snapshot, use stored score/total only for a specific nonmixed category. Ignore mixed-category fallback for category breakdown; show total legacy/incomplete snapshot count. Exclude invalid zero totals from percentage calculation and disclose incomplete rows rather than displaying NaN.

Preserve dashboard strong/weak at 80%; preserve `AnalyticsCard` per-exam strong at 90%, passing at 80%. These existing views use different labels deliberately for this scope. Empty history produces count/score 0, empty categories, empty seen/wrong sets.

After deleting any selected attempts, rebuild `user_progress` entirely from the surviving attempts in the same transaction. Order by `completed_at ASC, id ASC`; for every valid snapshot question add its ID to seen, and set latest outcome by question ID. Exact answer equality means correct; unanswered means wrong. Wrong contains only IDs whose last surviving answer is wrong. Deleting a later correct answer can therefore expose an earlier wrong answer again. Stable timestamp ties use attempt UUID; arrival/retry order must not change outcomes. Store deterministic sorted arrays.

Legacy rows without question IDs cannot reconstruct seen/wrong. Rebuild from usable surviving snapshots and set `progress_coverage='partial'` with incomplete count; disclose that older missing question history cannot be recovered. Do not retain predelete sets or guess IDs. Overall score analytics still include valid legacy score/total rows. New submissions require valid complete snapshots and server-validated score bounds/shape; grading remains client-side.

## Database authorization and resurrection fences

Use private tables for memberships, admin sessions/throttle, selection snapshots, operations/audit, user lifecycle, and attempt tombstones. Private schema is not an exposed PostgREST schema and has no anon/authenticated usage grants. Public wrappers are explicitly granted to `service_role` only for admin operations; wrappers validate service-role context plus current actor membership from a server-passed identity. Reviewer wrappers use verified `auth.uid()`. All SECURITY DEFINER functions pin an empty search_path and qualify tables/functions; revoke default PUBLIC execution. No role checks trust editable JWT metadata.

`private.user_data_state(user_id PK, generation bigint, revision bigint, status active|deleting|deleted, progress_coverage, incomplete_attempt_count)` deliberately has no cascading Auth FK. Seed generation/revision 0 for existing users; trusted signup trigger seeds new identities. Add `generation bigint` to attempts and active sessions; backfill existing rows to 0 but supply no client-side or SQL default for new writes. Attempt UUID is immutable. `private.attempt_tombstones(user_id,attempt_id PK pair,deleted_at,operation_id)` also survives Auth deletion. Keep these tiny records permanently in v1; there is no purge job.

Revoke authenticated/anon direct INSERT/UPDATE/DELETE grants and old mutation policies on `exam_attempts`, `user_progress`, and `active_sessions`; retain only owner SELECT with live-account/lifecycle checks. Direct old PostgREST clients fail permission checks, even if they omit generation or mint a new UUID. Generation is not inferred/defaulted on submission. Authenticated writes must use the new narrow reviewer RPCs; service credentials never enter the reviewer. Profile SELECT/UPDATE becomes owner-only with live-account checks, including UPDATE WITH CHECK; no profile INSERT/DELETE through browser. Reject stale JWT reads as well as writes by requiring a live `auth.users` row and lifecycle active in all personal-table policies/RPCs. Anonymous question-bank access stays unchanged.

Reviewer RPCs: `reviewer_data_state()`, `save_attempt(p_attempt jsonb)`, `save_active_session(p_session jsonb,p_generation bigint)`, `delete_active_session(p_session_id uuid,p_generation bigint)`. Each binds ownership to auth.uid(), verifies the live Auth row, locks the user's state row, requires active status and exact generation, and refuses tombstoned attempt IDs before checking duplicates. `save_attempt` atomically inserts/rebuilds progress/conditionally removes only the matching active session and increments revision. Duplicate identical attempt UUID returns the existing ID without changing progress/revision; conflicting snapshot reuse fails. Other mutation RPCs increment revision when state changes. No generic arbitrary-table or arbitrary-owner RPC.

Single/bulk exam delete locks the target state, checks current admin and sealed selection/revision, inserts all tombstones, deletes selected rows, rebuilds progress once, increments revision and commits operation/audit together. Full reset locks the same row, increments generation, deletes attempts/progress/active session, leaves an empty progress row, increments revision and audit in one transaction. It need not tombstone every old ID because old-generation writes are rejected. All related transactions use the same per-user lock; unaffected users are never reset or included. No network calls occur inside DB transactions.

## Reviewer integration and cross-device behavior

Wire the existing durable IndexedDB repository/coordinator through `syncStore.svelte.ts`; replace the old array queue/direct writes. Quiz starts with one UUID and fetched generation; final submission, retries and reload reuse that UUID, generation, and original completion timestamp. Never create a new UUID or relabel old-generation data to recover a rejection. Extend `SaveState` with `discarded` for terminal admin deletion/reset rejection; genuine transport/server failures stay durable queued. A failed durable write is an error, not saved. Use the current save indicator and retry affordance with accurate saving/queued/saved/discarded copy and unchanged geometry.

Namespace authenticated local active sessions by owner and persist `{version:2,ownerId,generation,sessionId,...snapshot}`; keep guest storage separate. Capture generation at start/restore, not completion. On auth resolution, before queue drain, on focus/online/pageshow, and every 60 seconds while visible and authenticated, fetch generation/revision through owner RPC. Changed revision refetches dashboard/history and server active-session state; changed generation clears only that owner's stale local/cloud-view state and old queued work, broadcasts invalidation to same-origin tabs, and prevents the in-flight exam saving. Tell the reviewer through existing status/dialogs that an administrator reset progress and the old exam must restart. Other-device offline displays may remain stale until reconnect; do not promise remote cache erasure.

An exam already in progress when only other completed attempts are deleted remains usable at the same generation. Its next save rebuilds from current DB history and cannot reintroduce tombstoned completed attempts. Reset invalidates all in-flight exams. Account deletion invalidates account caches and stops syncing; client signs out only the affected reviewer identity after authoritative terminal state. A response from an earlier user must not overwrite another user's state.

Legacy durable attempts missing generation may be imported deterministically with generation 0 only if an authoritative live state fetch confirms generation 0; never stamp them with current generation after reset. At generation >0 quarantine/drop with clear discarded status. Unknown-owner legacy active-session localStorage is quarantined; do not assign it to the next account. Existing owner-protected cloud paused sessions can be upgraded at their stored backfilled generation. Offline startup cannot infer ownership/generation, so it does not drain legacy records until online validation. Keep guest attempts and preferences untouched.

The questions API must read personalized progress only from a request-scoped verified bearer client and inferred auth.uid(); remove the shared server browser singleton and do not authorize via `userId` URL input. Preserve question selection behavior/weights. This narrow fix ensures rebuilt progress reaches the existing algorithm without cross-account state.

## Account deletion across Auth and Postgres

Auth admin deletion cannot share a DB transaction. First create a durable operation keyed by caller operation UUID, actor, target, and request fingerprint. In one locked DB transaction verify current admin/protected-target guard, typed email and recent reauth evidence; mark lifecycle `deleting`, increment generation/revision, remove app exam/progress/session/profile data, preserve fences/audit, and set `app_data_removed`. Commit before calling `auth.admin.deleteUser(targetId, false)` server-side. This immediately denies personal reads/writes even while Auth still exists. Do not claim account deletion complete yet.

Statuses: `prepared` → `app_data_removed` → `auth_delete_pending` → `complete`; failures after removal become `auth_delete_failed` with sanitized retryable error and attempt count. Store a short durable execution lease so concurrent retries cannot call Auth twice at once. A crashed process resumes on an explicit retry of the same operation through the console; no worker/queue service is needed. If Auth is already absent, verify that absence and complete. Unknown transport outcomes remain pending until checked. Never roll back generation/status or restore app data on Auth failure. Console plainly shows “Progress removed; account deletion pending/failed” and offers Retry. A DB failure before preparation means no Auth deletion; a DB failure after Auth success leaves a retryable reconciliation operation, never false success.

Finalization locks/rechecks target state, clears any residual app rows, marks lifecycle deleted, records immutable final audit, and retains fences and operation. Audit/table FKs must not prevent Auth deletion; update existing user_progress FK to ON DELETE CASCADE or explicitly remove its row before Auth. Protect existing storage objects: inspect whether any Storage buckets reference the target; if Auth reports an ownership dependency, show an actionable blocked failure rather than deleting unrelated storage. Supabase JWTs can remain cryptographically valid after account deletion, so live-row/lifecycle policies are mandatory, not just sign-out.

## Migration, verification, and rollout

Fresh local replay needs a baseline before existing `20260731_create_user_progress.sql`; create an idempotent `20260730_reviewer_baseline.sql` from actual root schema/session migrations with all expected columns. Preserve the existing migration file. A new `20261021_admin_console.sql` upgrades either baseline or manually initialized installations without dropping user data. Verify schema/constraint/policy state explicitly; remove old permissive policies by inspected names and assert no permissive write/public profile policies survive. Existing installations must baseline migration history only after schema inspection; do not rerun bootstrap/policy creation blindly. Document exact read-only inspection and approved application steps separately.

Use installed Vitest, fake-indexeddb and PGlite for pure/auth-mock/database tests. PGlite fixtures model auth.users, auth.uid(), auth.jwt(), anon/authenticated/service_role and grants/RLS; they do not prove GoTrue/PostgREST/Storage behavior. Before live deployment, run a disposable real Supabase test with two reviewer users plus separate admin, direct legacy PostgREST calls, revoked membership and stale JWTs, Auth deletion failure/retry, and migration rehearsal against a schema/data snapshot. No production test deletion.

Required checks: all current question/unit tests, targeted integration tests, `npm run check`, `npm run build`, client bundle secret scan, and browser desktop/mobile checks. Current checkpoint records four existing type errors; capture current baseline, fix new errors, and report remaining baseline errors rather than claiming a clean check. Browser verification covers concurrent isolated admin/Google logins, selection scopes, double-confirm deletion, keyboard dialogs, stale/offline/two-tab recovery, unaffected user B and unchanged reviewer screens. Simulated viewport checks are not physical-device checks.

Deployment approval is separate from plan/implementation approval. The adapter-auto deployment target must support SvelteKit server routes and private environment secrets; a static-only host cannot operate this console. Deployment requires coordinated migration/client release because old reviewer direct writes intentionally fail after grants are revoked. Rehearse backup/restore; once destructive operations occur, rollback must never restore tombstoned attempts or remove generation/lifecycle fences. Do not enable admin destructive actions until DB fences and reviewer integration are both live.
